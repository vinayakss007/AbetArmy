# Craq: Full-stack entrepreneur social platform

A greenfield social Q&A platform for entrepreneurs with an Express/TypeScript backend, Next.js 14 frontend, and Docker Compose infrastructure. The backend provides JWT-authenticated REST APIs for issues, solutions, threaded comments, voting, tools directory, full-text search, file uploads, and a multi-provider AI gateway with streaming. The frontend consumes these via Axios with Zustand for auth state and WebSocket for real-time notifications.

Watch for: hardcoded JWT fallback secrets that ship in Docker Compose and never fail closed (confirmed); missing authorization checks that allow any authenticated user to mutate any other user's content (confirmed); S3 upload implementation that sends unauthenticated requests without AWS Signature V4 (confirmed); AI chat endpoint that proxies arbitrary user-supplied system prompts to LLM providers without sanitization or cost controls (confirmed); vote counter race conditions under concurrent writes (likely); Docker Compose health check path mismatch that prevents the stack from becoming healthy (confirmed).

## High-level view

The authentication layer uses bcrypt + JWT access/refresh tokens with a hardcoded `'dev-secret-key'` fallback. The Docker Compose environment also ships a `'change-me-in-production'` default. Neither the middleware nor the service refuse to start when the secret is a known default, so a deployment that forgets to override environment variables runs with a guessable signing key.

Authorization is almost entirely absent below the "is the user logged in?" gate. Update and delete endpoints for issues, solutions, comments, and profiles authenticate the caller but never verify they own the resource. Any logged-in user can edit or delete another user's content.

The AI gateway implements multi-provider fallback with retry logic and streaming, but the `/api/ai/chat` endpoint accepts arbitrary messages arrays including system prompts from the client. There is no per-user rate limiting, no token budget, and no cost ceiling — a single user can exhaust provider API credits.

The voting system maintains denormalized counters on the issues and solutions tables. The check-then-act pattern (SELECT existing vote, then UPDATE counter) is not wrapped in a transaction, so concurrent votes on the same target can leave counters out of sync with the votes table.

The S3 upload path does a raw `fetch PUT` without AWS Signature V4 authentication. This will always fail against real S3 or any S3-compatible service that enforces auth. The local upload path works but writes to the container filesystem, which is ephemeral without a volume mount in Docker Compose.

The frontend stores tokens in localStorage and also checks cookies in Next.js middleware, but no code ever sets a cookie — the middleware guard will never find a token and always redirect on protected paths.

The Docker Compose stack cannot become healthy: the backend health check hits `/api/health` but the Express app exposes `/health`. The frontend depends on `backend: condition: service_healthy`, so the entire compose stack stalls on startup.

1. **Hardcoded JWT secret fallback** (confirmed) — `auth.service.ts` and `auth.ts` middleware fall back to `'dev-secret-key'` when `JWT_SECRET` is unset. Docker Compose defaults to `'change-me-in-production'`. Add startup validation that refuses to boot with known-default secrets in production.

3. **AI chat proxies arbitrary system prompts** (confirmed) — `/api/ai/chat` passes user-supplied `messages` (including system role) directly to LLM providers. Restrict or sanitize the system role; add per-user rate limits and token budget caps.
4. **S3 upload lacks auth signing** (confirmed) — `uploadToS3` does a plain `fetch PUT` without AWS Signature V4. Replace with the AWS SDK or implement SigV4 manually.
5. **Vote counter race condition** (likely) — `vote.service.ts` reads existing vote then updates counters outside a transaction. Wrap the read-check-write-update sequence in `BEGIN`/`COMMIT` with `SELECT ... FOR UPDATE` or use atomic SQL.
6. **Frontend cookie/localStorage mismatch** (confirmed) — `middleware.ts` checks `request.cookies.get('access_token')` but `authStore.ts` writes to `localStorage` only. Protected route guards never pass. Set the cookie on login or switch middleware to a different check.
7. **Upload volume not mounted** (confirmed) — Docker Compose has no volume for the backend `uploads/` directory. Container restarts lose all uploaded files. Add a named volume or bind mount.
8. **No content-length cap on AI prompt payloads** (likely) — The chat and summarize endpoints accept unbounded string arrays. A large payload could hit upstream token limits and incur unexpected cost. Add a content-length or token-count cap.
9. **Google OAuth route is a stub** (confirmed) — `GET /api/auth/google` returns a JSON message instead of redirecting to Google. The callback handler assumes a `req.user` that Passport would populate, but Passport is never configured. Remove or properly wire up.
10. **Docker health check path mismatch** (confirmed) — Docker Compose checks `http://localhost:4000/api/health` but Express registers `/health`. The container never becomes healthy, blocking the frontend from starting. Change one to match the other.
11. **Meilisearch provisioned but unused** (confirmed) — Docker Compose runs a Meilisearch container and passes `MEILI_HOST`/`MEILI_MASTER_KEY` to the backend, but search.service.ts queries PostgreSQL directly. Remove the container or integrate it.

## JWT secrets and startup posture

The auth service declares secrets at module scope:

```typescript
const JWT_SECRET = process.env.JWT_SECRET || 'dev-secret-key';
const JWT_REFRESH_SECRET = process.env.JWT_REFRESH_SECRET || 'dev-refresh-secret-key';
```

The auth middleware duplicates this:

```typescript
const JWT_SECRET = process.env.JWT_SECRET || 'dev-secret-key';
```

Docker Compose sets `JWT_SECRET: ${JWT_SECRET:-change-me-in-production}`. If an operator deploys without an `.env` file, the system runs with a publicly known signing key. There is no startup check that aborts when `NODE_ENV=production` and the secret matches a known default. The consequence is that an attacker can forge valid access tokens for any user ID without ever authenticating.

## Missing ownership authorization

Every mutation endpoint authenticates the caller (requires a valid JWT) but never checks whether the caller owns the resource being modified:

- `PUT /api/issues/:id` and `DELETE /api/issues/:id` pass `req.params.id` straight to `issueService.update` / `issueService.delete`.
- `PUT /api/comments/:id` and `DELETE /api/comments/:id` do the same.
- `PUT /api/users/:id` allows any authenticated user to update any profile — name, bio, avatar, skills.

The pattern is consistent: the controller extracts the resource ID from the URL, calls the service, and the service performs the mutation without comparing `author_id` to the token's `userId`. This is an escalation-of-privilege gap where any registered user can modify or destroy content belonging to others.

## AI gateway as open proxy

The `/api/ai/chat` endpoint accepts:

```typescript
const chatSchema = z.object({
  body: z.object({
    messages: z.array(
      z.object({
        role: z.enum(['system', 'user', 'assistant']),
        content: z.string(),
      })
    ).min(1),
    stream: z.boolean().optional(),
    temperature: z.number().min(0).max(2).optional(),
    maxTokens: z.number().min(1).optional(),
  }),
});
```

Any authenticated user can supply arbitrary system prompts, set `maxTokens` without an upper bound, and stream responses. The global rate limiter (100 requests per 15 minutes across all endpoints) is the only control. A motivated user can exhaust monthly API credits for all configured providers by looping large `maxTokens` requests. There is no per-user quota, no prompt sanitization, and no total-token accounting.

The streaming path also lacks fallback: `chatStream` only uses `providers[0]` and does not retry on failure, unlike the non-streaming path which iterates the full fallback chain.

## Vote counter atomicity

In `vote.service.ts`, the vote operation executes multiple queries sequentially:

```
1. SELECT existing vote
2. DELETE or UPDATE the vote record
3. UPDATE target table SET upvotes/downvotes = upvotes/downvotes + delta
```

None of these are in a transaction. Two concurrent upvotes on the same issue can both see "no existing vote", both insert (one will fail on the UNIQUE constraint, but the counter increment may already have fired), and the counter drifts from ground truth. The same race applies to toggle-off. Using `BEGIN`/`COMMIT` with row-level locking, or a single atomic upsert with a trigger for counter maintenance, would close this gap.

## S3 upload without authentication

`uploadToS3` constructs a URL and does:

```typescript
const response = await fetch(url, {
  method: 'PUT',
  headers: {
    'Content-Type': contentType,
    'x-amz-acl': 'public-read',
  },
  body: buffer,
});
```

Real S3 requires AWS Signature V4 on every request. This request will be rejected with a 403 by any standard S3 endpoint. The code comments acknowledge this ("simplified implementation; production would use AWS SDK") but the feature is wired into the upload route and Docker Compose environment without any guard preventing its use. If `STORAGE_TYPE=s3` is set, all uploads silently fail.

Additionally, the local storage path writes to `process.cwd() + '/uploads'` inside the Docker container, but Docker Compose defines no volume for that path. Files survive only until the container restarts.

## Frontend auth flow mismatch

The Next.js middleware checks:

```typescript
const token = request.cookies.get('access_token')?.value;
```

But the Zustand auth store writes:

```typescript
localStorage.setItem('access_token', accessToken);
```

Cookies and localStorage are different storage mechanisms. No code ever sets the `access_token` cookie (there is no `Set-Cookie` header from the backend, nor a `document.cookie` write in the frontend). The middleware will always see `token` as undefined, and protected routes (`/issues/new`, `/profile/edit`) will always redirect to login even for authenticated users.

## Docker Compose health check path discrepancy

The backend health check in Docker Compose hits `http://localhost:4000/api/health`, but the Express app registers the health endpoint at `/health` (not `/api/health`). The container will never pass its health check, blocking the frontend service from starting (it depends on `backend: condition: service_healthy`).

```yaml
test: ['CMD', 'wget', '--no-verbose', '--tries=1', '--spider', 'http://localhost:4000/api/health']
```

vs.

```typescript
app.get('/health', (_req, res) => { ... });
```

## Search service ignores Meilisearch

Docker Compose provisions a Meilisearch container, and the environment passes `MEILI_HOST` and `MEILI_MASTER_KEY` to the backend. But `search.service.ts` performs all searches directly against PostgreSQL with `to_tsvector`/`plainto_tsquery`. Meilisearch is never referenced in the backend code. The container runs unused, consuming memory.
